# DECISIONS.md

## Вариант

Номер варианта: 4

Часть А: правило R5 изменено. `STANDARD` возвращается только для заявки, у которой `amount < 50000`, `urgent == false`, `risk == RiskLevel.LOW` и отсутствуют персональные данные. Если заявка дошла до R5, но не соответствует этим условиям, уровень риска `MEDIUM` направляется в `DIRECTOR_REVIEW`, а сумма от 50000 рублей при `LOW` направляется в `FINANCE_REVIEW`.

Часть Б: добавлен метод `addStandardEligibility(long amount, boolean urgent, RiskLevel risk, boolean containsPersonalData)`. Он возвращает `true` только при одновременном выполнении четырёх условий стандартного маршрута.

## Решение 1

Проверка изменённого R5 выполняется после правил R1-R4. Сначала сохраняются базовые приоритеты: персональные данные направляются в `SECURITY_REVIEW`, высокий риск — в `DIRECTOR_REVIEW`, сумма от `FINANCE_LIMIT` — в `FINANCE_REVIEW`, срочная заявка — в `FAST_TRACK`. Затем вызывается `addStandardEligibility`.

Альтернатива: поставить новое условие `STANDARD` до правил R1-R4.

Выбран порядок после R1-R4, потому что вариант изменяет только правило R5 и не отменяет более приоритетные правила. Так заявка с персональными данными или высоким риском не сможет ошибочно попасть в стандартный маршрут.

## Решение 2

Для заявок, которые дошли до R5, но не подходят под `STANDARD`, используется однозначное распределение. `risk != LOW` ведёт в `DIRECTOR_REVIEW`; при `LOW` и сумме от 50000 рублей выбирается `FINANCE_REVIEW`.

Альтернатива: всегда возвращать `FINANCE_REVIEW` для любого нарушения условий `STANDARD`.

Выбранное решение учитывает причину отказа от стандартного маршрута: повышенный уровень риска требует директорского рассмотрения, а превышение лимита стандартной заявки — финансового контроля. При одновременном нарушении условий риск проверяется первым, что согласуется с базовым приоритетом R2 над R3.

## Граничные значения

Граница стандартного маршрута проверяется с обеих сторон.

Заявка с `amount = 49999`, `urgent = false`, `risk = LOW` и без персональных данных получает `STANDARD`.

Заявка с теми же параметрами и `amount = 50000` уже не соответствует условию `amount < 50000` и получает `FINANCE_REVIEW`.

Значение `amount = 0` допустимо и при нейтральных параметрах получает `STANDARD`.

Отрицательная сумма отклоняется до применения правил маршрутизации.

Значение `risk == null` также отклоняется защитной проверкой.

Уровень `MEDIUM` не соответствует условию `risk == LOW`, поэтому после R1-R4 заявка направляется в `DIRECTOR_REVIEW`.

Срочная заявка по-прежнему обрабатывается правилом R4 и получает `FAST_TRACK`, если более приоритетные правила не сработали.

## Покрытие проверками

Первые 13 проверок `SelfCheck` сохраняют набор сценариев методички.

Ожидание для `MEDIUM` обновлено в соответствии с вариантом 4.

Проверка 14 подтверждает включение значения 49999 в `STANDARD`.

Проверка 15 подтверждает исключение значения 50000 из `STANDARD` и переход в `FINANCE_REVIEW`.

Проверка 16 вызывает `addStandardEligibility` для полностью подходящей заявки и ожидает `true`.

Проверка 17 вызывает метод для заявки с персональными данными и ожидает `false`.

Файл `data/sample.csv` сохраняет базовые сценарии и добавляет четыре строки для новой логики.

Data-driven-режим сравнивает фактический маршрут с колонкой `expected`.

Ошибочные входные данные обозначаются значением `ERROR`.

Таким образом, отдельно проверяются базовые приоритеты, границы, защитные условия и обе части индивидуального варианта.

## Ответы на контрольные вопросы

### Вопрос 1

Наиболее важной защитной проверкой является валидация `risk == null`. Она расположена в методе `route` класса `ApprovalRouter` и выполняется до правил R1-R5. Если уровень риска не передан, метод выбрасывает `IllegalArgumentException` с понятным сообщением. Такая ошибка вероятна при ручном вводе или чтении данных из внешнего файла: вызывающий код может пропустить обязательное значение. Ранняя проверка не позволяет продолжить маршрутизацию с неопределённым риском и предотвращает случайное попадание заявки в `STANDARD`, `FINANCE_REVIEW` или другой маршрут.

### Вопрос 2

Ключевое бизнес-правило находится в методе `route` класса `ApprovalRouter`. Этот метод выбирает ровно один маршрут и сохраняет приоритет R1-R4, после чего применяет изменённое правило R5 варианта 4. Проверка стандартной допустимости вынесена в `addStandardEligibility`, но окончательное решение остаётся в `route`. Такое размещение удобно, потому что класс отвечает только за маршрутизацию, а единая точка принятия решения легко проверяется через `SelfCheck`, используется в data-driven-режиме и не требует дублирования условий в других классах.

### Вопрос 3

На Activity-диаграмме ромб «Подходит для STANDARD?» соответствует вызову `addStandardEligibility(amount, urgent, risk, containsPersonalData)` в методе `route`. Ветвь «да» возвращает `STANDARD`. По ветви «нет» выполняется дополнительная проверка уровня риска: `MEDIUM` направляется в `DIRECTOR_REVIEW`, а заявка с `LOW`, не прошедшая из-за суммы, — в `FINANCE_REVIEW`. Таким образом, диаграмма показывает не только последовательность операторов `if`, но и конкретный путь исполнения для изменённого правила R5 варианта 4.

### Вопрос 4

Минимальное изменение затронет границу стандартного маршрута. Сейчас она хранится в константе `STANDARD_LIMIT` класса `ApprovalRouter` и используется методом `addStandardEligibility`. Если преподаватель предложит заменить 50000 на другое значение, достаточно изменить одну константу и соответствующие граничные ожидания в тестовых данных. Остальные классы, перечисления и порядок R1-R4 менять не потребуется. Такое решение уменьшает число правок, сохраняет структуру бизнес-логики и снижает вероятность расхождения между основной маршрутизацией и отдельной проверкой допустимости `STANDARD`.

## Фрагмент кода для анализа

Проблема фрагмента заключается в неверном порядке проверок: `urgent` проверяется раньше `containsPersonalData`, хотя R1 имеет более высокий приоритет, чем R4. Для `10000;true;LOW;true` ошибочный код вернёт `FAST_TRACK` вместо `SECURITY_REVIEW`. Исправленный порядок начинается с `containsPersonalData`, затем проверяет высокий риск, сумму, срочность и только после этого изменённый R5.
